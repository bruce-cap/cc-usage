# CC Usage VS Code Plugin PRD

## 1. 文档信息

- 文档名称：CC Usage VS Code 插件产品需求文档
- 文档版本：v0.1
- 文档日期：2026-04-28
- 适用阶段：首版原型到可本地自用版本
- 当前状态：草案

## 2. 项目背景

`cc-usage` 当前是一个本地用量看板工具。它会扫描 `~/.claude/projects` 下的 Claude Code 会话日志，聚合模型调用的 token 使用情况，再通过本地 HTTP 服务把结果展示在浏览器页面中。

这个实现已经能解决“看日志”和“看汇总”两个核心问题，但它还有一个明显短板：用户必须先启动本地服务，再打开浏览器页面，整个使用过程和日常 IDE 工作流是割裂的。

当前项目的核心价值并不在“浏览器服务”本身，而在“本地日志扫描 + 用量聚合 + 简单看板展示”这条链路。现有仓库已经有相对清晰的模块边界：

- `src/usage-aggregator.js`：负责扫描和聚合用量数据
- `src/report-payload.js`：负责生成前端消费的数据结构
- `src/live-report-server.js`：负责提供本地 HTTP 接口
- `public/index.html`：负责浏览器端看板展示

这意味着当前项目具备升级为 VS Code 插件的基础。首版产品不需要重写核心聚合逻辑，只需要把“浏览器页面 + HTTP 服务”的使用形态，迁移成“VS Code 侧边栏面板 + 扩展宿主调用本地聚合逻辑”的形态。

## 3. 产品目标

### 3.1 总体目标

把 `cc-usage` 升级为一个可在 VS Code 中本地运行的侧边栏插件，让用户不离开 IDE 就能查看 Claude Code 的本地用量统计。

### 3.2 首版目标

首版插件需要实现以下目标：

1. 在 VS Code 侧边栏中提供一个独立的 `CC Usage` 面板。
2. 默认读取 `~/.claude/projects` 作为日志源目录。
3. 在面板中展示近期用量仪表盘。
4. 支持用户手动刷新数据。
5. 支持插件自动刷新，刷新周期固定为 2 分钟。
6. 在本地开发模式下可运行、可调试、可验证。

### 3.3 非目标

首版明确不做以下内容：

1. 不支持自定义日志目录。
2. 不支持多目录聚合。
3. 不支持 JetBrains、Cursor 独立适配。
4. 不支持 VS Code Marketplace 发布流程优化。
5. 不支持账号体系、云端同步、远程存储。
6. 不支持复杂图表库、拖拽筛选、跨项目对比。
7. 不支持历史快照保存和趋势预警。

## 4. 目标用户

### 4.1 主要用户

首版主要用户就是当前项目作者本人，也就是在本地长期使用 Claude Code，并且希望在开发时直接查看模型用量的人。

### 4.2 用户特征

目标用户具备以下特征：

- 日常工作主场景在 VS Code 内
- 已经使用 Claude Code，并且本机存在 `~/.claude/projects` 日志目录
- 希望减少“切浏览器”“手动起服务”的动作
- 更关注快速查看和低摩擦使用，而不是复杂分析功能

## 5. 用户痛点

当前工具虽然可用，但用户在使用过程中仍然存在以下痛点：

1. 需要显式启动本地服务，存在额外操作成本。
2. 需要切换到浏览器查看，不在 IDE 主工作流内。
3. 本地服务模式更像开发工具原型，不像一个长期可用的 IDE 插件能力。
4. 用户查看频率可能很高，但当前入口不够顺手。
5. 对于不熟悉命令行或本地服务的用户，启动路径不够直观。

## 6. 核心用户故事

### 6.1 主用户故事

作为一个日常在 VS Code 里使用 Claude Code 的用户，我希望在侧边栏直接看到近期 token 用量和模型分布，这样我就不用启动额外服务，也不用离开 IDE。

### 6.2 补充用户故事

1. 作为用户，我希望打开 VS Code 后就能在侧边栏看到这个面板，而不是再去浏览器找页面。
2. 作为用户，我希望插件能自动刷新数据，这样我不需要频繁手动刷新。
3. 作为用户，我希望在觉得数据过期时，可以手动刷新一次。
4. 作为用户，我希望插件默认就能工作，不需要先配置路径。
5. 作为用户，我希望在日志目录不存在或者读取失败时，能看到清晰的错误提示。

## 7. 使用场景

### 7.1 日常查看

用户在写代码时，顺手打开 VS Code 左侧边栏中的 `CC Usage` 面板，查看最近 7 天、30 天或全部时间范围的 token 使用概览。

### 7.2 会话后复盘

用户在一次高强度使用 Claude Code 之后，打开侧边栏面板查看当天或最近几天的 token 消耗变化，并观察主要模型占比。

### 7.3 开发调试

用户在调试自己的 Claude 工作流时，希望快速知道近期调用量有没有明显变化，因此需要一个低成本、可随时刷新的视图。

## 8. 功能范围

### 8.1 首版必须具备的功能

#### 8.1.1 侧边栏入口

插件安装并启用后，VS Code 左侧 Activity Bar 或侧边栏中应出现 `CC Usage` 入口。用户点击后，可以展开对应面板。

#### 8.1.2 面板展示

面板内需要展示以下信息：

- 统计时间窗口切换：`All`、`30d`、`7d`
- 总 Token
- 输入 Token
- 输出 Token
- 成本信息
- 按日期的简单柱状图或趋势图
- 按模型的使用分布列表
- 数据生成时间
- 扫描文件数量

#### 8.1.3 自动刷新

插件在面板初始化后，应每 2 分钟自动刷新一次数据。

#### 8.1.4 手动刷新

面板中需要提供手动刷新按钮，用户点击后应立即触发一次重新聚合。

#### 8.1.5 默认数据源

插件默认使用 `~/.claude/projects` 作为日志目录，不提供首版可视化配置入口。

#### 8.1.6 错误提示

当插件无法找到日志目录、无权限读取目录、日志解析失败或无有效数据时，面板中应显示可读提示，而不是空白页。

### 8.2 首版可选但不强制实现的功能

1. 在状态栏显示简短摘要。
2. 增加“最后刷新时间”独立显示。
3. 增加数据为空时的引导文案。
4. 增加点击模型名称后的详情视图。

### 8.3 后续版本功能

1. 支持插件设置中自定义日志目录。
2. 支持多个目录聚合。
3. 支持导出 JSON 或静态 HTML。
4. 支持按工作区或项目维度筛选。
5. 支持更丰富的图表。
6. 支持发布到 VS Code Marketplace。

## 9. 用户流程

### 9.1 首次使用流程

1. 用户在本地安装插件开发版。
2. 用户打开 VS Code。
3. 用户在侧边栏看到 `CC Usage` 面板入口。
4. 用户点击入口，插件初始化界面。
5. 插件自动读取 `~/.claude/projects`。
6. 插件聚合数据并渲染仪表盘。
7. 插件启动 2 分钟自动刷新计时。

### 9.2 日常使用流程

1. 用户打开侧边栏面板。
2. 用户查看默认视图。
3. 用户切换 `All`、`30d`、`7d` 时间窗口。
4. 用户在需要时点击“刷新”按钮。
5. 插件重新读取本地日志并更新界面。

### 9.3 异常流程

1. 如果默认日志目录不存在，面板显示“未找到日志目录”。
2. 如果目录可读但没有可聚合数据，面板显示“没有找到可聚合记录”。
3. 如果解析过程中出现异常，面板显示“加载失败”以及简短错误信息。

## 10. 交互要求

### 10.1 交互原则

首版交互应遵循“低摩擦、少配置、即开即看”的原则。

### 10.2 具体交互要求

1. 面板加载时应显示加载状态。
2. 刷新进行中应禁用刷新按钮，避免重复触发。
3. 时间窗口切换应在当前已加载数据上即时完成，不需要重新扫描目录。
4. 自动刷新和手动刷新共用同一套数据加载逻辑，避免逻辑分叉。
5. 当读取失败时，错误提示应保留在面板中，直到下次成功刷新。

## 11. 界面要求

### 11.1 首版界面策略

首版优先复用现有 `public/index.html` 的布局结构和视觉表达，但需要适配 VS Code Webview 环境。

### 11.2 界面组成

面板应至少包含以下区域：

- 顶部标题区
- 时间窗口切换按钮区
- 手动刷新按钮区
- 元信息区
- 指标卡片区
- 按日期图表区
- 模型分布列表区
- 空状态或错误提示区

### 11.3 适配要求

1. 面板需要适配侧边栏的窄宽度。
2. 面板应尽量兼容浅色和深色主题。
3. 在数据量较多时，图表区域应保持可读性。
4. 文本和按钮在较小宽度下不能明显溢出。

## 12. 数据与技术约束

### 12.1 数据来源约束

首版只依赖本地文件系统中的 Claude Code 会话日志，不接入任何网络服务。

### 12.2 技术基础约束

当前项目只使用 Node.js 内置模块，没有第三方运行时依赖。升级为 VS Code 插件时，应尽量保留这个轻量特点，避免在首版引入不必要的重型依赖。

### 12.3 结构约束

首版应尽可能复用现有聚合逻辑，而不是重写一套新逻辑。推荐保留以下分层思路：

- 核心层：日志扫描和聚合
- 插件层：VS Code 激活、侧边栏注册、消息通信、刷新调度
- 展示层：Webview HTML/CSS/JS

### 12.4 运行约束

插件应在本地桌面版 VS Code 中运行，优先面向 Windows 环境验证。首版不承诺兼容远程开发容器、浏览器版 VS Code 或 Web 扩展模式。

## 13. 成功标准

首版完成后，应满足以下验收标准：

1. 插件可以在本地开发模式下被 VS Code 正常加载。
2. 侧边栏能看到 `CC Usage` 面板入口。
3. 面板打开后可以读取 `~/.claude/projects` 并展示数据。
4. 用户可以切换 `All`、`30d`、`7d` 视图。
5. 用户可以手动刷新数据。
6. 插件会每 2 分钟自动刷新一次。
7. 在目录不存在、无数据或解析异常时，界面能给出明确反馈。
8. 核心统计结果与现有浏览器版工具保持一致或可接受一致。

## 14. 验收口径

### 14.1 功能验收

- 插件开发宿主可以正常启动
- 扩展激活没有阻塞性报错
- 侧边栏视图可以打开
- 数据可以正常加载和刷新

### 14.2 数据验收

- 同一批日志输入下，插件版和当前本地服务版的汇总结果应基本一致
- 模型分布和总 token 统计不能出现明显偏差

### 14.3 体验验收

- 首次打开无需额外配置
- 手动刷新行为明确
- 自动刷新不会造成明显卡顿

## 15. 风险与问题

### 15.1 已知风险

1. VS Code Webview 环境和普通浏览器环境不同，现有页面脚本需要做宿主适配。
2. 侧边栏宽度比浏览器页面更窄，当前图表布局可能需要调整。
3. 如果日志目录很大，首次扫描速度可能影响面板打开体验。
4. 如果未来 Claude 本地日志结构变化，插件聚合逻辑也需要同步调整。

### 15.2 当前未决问题

1. 插件入口最终放在 Activity Bar 独立图标下，还是放在已有 Explorer 下属视图，目前尚未定。
2. 首版是否需要增加“上次刷新时间”的更显式展示，目前尚未定。
3. 首版是否需要保留现有本地 HTTP 服务模式并与插件模式共存，目前尚未定。

## 16. 产品决策摘要

本 PRD 对首版产品作出以下明确决策：

1. 首版目标是 VS Code 插件，不是网页工具增强版。
2. 首版以侧边栏仪表盘为主，不以命令面板为主。
3. 首版默认读取 `~/.claude/projects`，不开放路径配置。
4. 首版支持 2 分钟自动刷新和手动刷新。
5. 首版主要面向个人本地使用和开发验证，不以 Marketplace 发布为目标。
6. 首版优先复用现有聚合逻辑和现有页面结构，降低改造成本。

## 17. 建议的下一步

PRD 确认后，下一步应进入实现方案设计，而不是直接编码。建议按以下顺序推进：

1. 先写技术设计文档，明确 VS Code 插件结构、目录划分、激活流程、Webview 通信方式。
2. 再拆实现计划，分阶段完成脚手架、数据接入、UI 迁移、刷新机制和调试验证。
3. 最后再开始正式编码。
